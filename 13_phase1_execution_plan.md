WP-1's README must document the required local Postgres version and basic setup so developer machines don't silently drift from CI. The test connection string is supplied via environment/configuration (e.g. `ConnectionStrings:IntegrationTestDb`, or an environment variable read by the test host), never hardcoded in test code. If the configured test database is unreachable, integration tests must **fail loudly** (a clear connection-error test failure) — never silently skip, which would create false local confidence while CI (always provisioned) actually runs them. Each test run must start from a clean, known database state: this plan specifies **Respawn** (or an equivalent truncate-based reset library) to reset all tables between test runs/collections, rather than a full migration-down-up cycle per test — Respawn-style truncation is markedly faster for a growing schema and keeps tests isolated without repeatedly paying migration cost; a full migration down/up remains an acceptable fallback if Respawn proves impractical for a specific case, but truncation-based reset is the default. Respawn configuration must explicitly exclude `__EFMigrationsHistory` from its reset/truncation set (a known Respawn gotcha — truncating it would wipe EF Core's migration-tracking state every run) and must correctly reseed/reset sequence-backed tables (e.g. `garage_sequences`, §36) so WP-3B's concurrency test isn't skewed by stale sequence state. `GarageOS.Tests.Integration` test collections that share the database must not run in parallel against it (disable collection parallelization for the integration project, or otherwise scope resets so concurrent collections can't interfere) — this must be stated explicitly in the project's test configuration, not left implicit. In CI, PostgreSQL is provisioned using the CI provider's native service-container support — for GitHub Actions, the built-in `services:` Postgres service (pinned to the same major version, 15+) in the workflow YAML, running on an `ubuntu-latest` (Linux-hosted) runner. This runs on the hosted runner's own infrastructure (GitHub's runner image itself provides the container runtime backing `services:` — this is a runner feature, not a project-level Docker dependency) and requires no separate Docker installation or Docker dependency from developers or from the project; developers never install or invoke Docker to run tests, locally or in CI. Integration tests must run against real PostgreSQL, not an in-memory/SQLite substitute, since the schema (§9) relies on PostgreSQL-specific types/behavior an in-memory provider would not exercise faithfully.

The `GarageOS.Tests.Unit`/`GarageOS.Tests.Integration` trivial tests are harness-proof only — they exist to prove the test infrastructure itself works (project wiring, `dotnet test`, CI execution, WebApplicationFactory + real-PostgreSQL plumbing including the reset mechanism), not to pad coverage numbers. ### WP-3B — Account/Garage Provisioning Service
- **Objective:** Internal `AccountProvisioningService.CreateGarageUnderAccount(accountId, garageDetails)` service method. No public HTTP endpoint is required in Phase 1 (garage provisioning is invoked internally — e.g. by the seed script now, and later by the Phase 6 signup/billing flow). Under a single database transaction, the method checks whether the account already owns a non-deleted garage (e.g. `SELECT ... WHERE account_id = @id AND deleted_at IS NULL FOR UPDATE` or an equivalent locking read) and rejects the call if one exists. **This is the only code path permitted to insert into `garages`.**
- **Responsible specialist:** Backend Engineer (schema/index support from Database Engineer)
- **Dependencies:** WP-3.
- **Files/modules created:** `Application/Accounts/AccountProvisioningService.cs` (or equivalent application-service location), any supporting index needed for the locking existence check (Database Engineer), update to WP-3's seed-data script to call this service instead of a raw insert.
- **Acceptance criteria:** A second `CreateGarageUnderAccount` call against the same account is rejected; a call against a different account succeeds; a concurrency test issuing two simultaneous `CreateGarageUnderAccount` calls for the same account confirms only one garage is ever created (proves the locking read actually prevents the race, not just the sequential case); WP-3's seed-data script is updated to call this service rather than performing a raw insert into `garages`.
- **QA requirement:** Unit tests for the single-garage rejection and cross-account success cases; an integration test for the concurrency case above. Plus an automated regression check (a repository-boundary/architecture test, or a CI grep for raw `INSERT INTO garages`/`dbContext.Garages.Add` outside this service's file) proving no other code path can insert into `garages` — this must not rest on a one-time manual code-walk alone, matching the standard already applied to WP-5's bypass-protection test and WP-6/WP-7's CI grep checks (see WP-9).
- **Security-review requirement:** Confirm no other repository/service method, migration, or seed path can insert into `garages` outside this service (this is what makes the one-garage-per-account rule enforceable at all, given it's an application-layer check, not a DB constraint) — confirmed via the automated check above, not code review alone.
- **Note — multi-location extension point:** the one-garage cardinality check lives entirely in this one service method, not in the schema. Enabling N garages per account later is a one-line relaxation of this method's check (or removing the check entirely), never a migration. This is the concrete, intentional extension point for future multi-location ownership referenced throughout this plan.

### WP-4 — Authentication
- **Objective:** JWT issuance (access + rotating/revocable refresh tokens), password hashing, `login`/`refresh`/`logout`/`forgot-password`/`reset-password`/`me` endpoints for garage-tenant users (§11). Owns `JwtOptions` (issuer/audience/signing-key configuration), using the general options-binding pattern WP-2 establishes — this is the one option class in this plan that is both secret-bearing and WP-4's alone to own (see WP-2/WP-7 ownership notes; no package owns both `JwtOptions` and `BrandingOptions`). Also owns the distinct platform-admin JWT claim/`aud` design and the policy-level separation between platform-admin and garage-tenant tokens, per §60/DECISIONS.md #4 — validated entirely through automated tests using **test-only JWT construction**, not a live HTTP endpoint. `Jwt:Issuer`/`Jwt:Audience` are read from configuration per §7A (never hardcoded to a brand string).
- **Scope correction (security finding, backend-engineer + security-reviewer):** this WP does **not** build or expose a live, customer/admin-reachable `POST /api/v1/platform/auth/login` or any other platform-admin-facing route in Phase 1. (The prior version of this WP described "a separate login/token path for platform admins issuing the distinct claim," which read as a live endpoint and conflicted with DECISIONS.md #4, which defers platform-admin UI/endpoints to Phase 6.) What ships in Phase 1 is: the `platform-admin` claim/`aud` design itself, the token-issuance code capable of producing such a claim, and a test-only helper for constructing platform-admin-claim tokens in the test suite — no reachable route. MFA, rate-limiting, audit-logging, secure account recovery, and session/token-security requirements for a live platform-admin login must all be satisfied before that endpoint goes live in Phase 6 — none of it is required now precisely because nothing is live now. Both Backend Engineer and Security Reviewer independently confirmed no Phase 1 requirement needs a live platform-admin login. **If this is ever disputed, it must be escalated to the Owner explicitly — it must not be assumed or silently reversed.**
- **Responsible specialist:** Backend Engineer
- **Dependencies:** WP-3.
- **Files/modules created:** `AuthController` (garage-tenant endpoints only — no `PlatformAdminAuthController`, since no live platform-admin route ships in Phase 1), `TokenService` (capable of issuing both garage-tenant and platform-admin-claim-shaped tokens), `RefreshTokenRepository`, password hasher wrapper, rate-limiting policy config for auth endpoints (§31), `JwtOptions.cs`, a test-only platform-admin token-construction helper living in the test project.
- **Acceptance criteria:** Login returns a valid JWT + rotates refresh token on use; a platform-admin-claim token (constructed via the test-only helper) fails every garage-tenant-scoped policy check, and a garage-tenant token fails a representative platform-admin policy — both asserted by automated tests, not a live HTTP round trip and not just code-review assertion; changing `Jwt:Issuer`/`Jwt:Audience` in configuration alone changes token validation behavior with no code edit; forgot-password gives an **identical response body and identical HTTP status** whether or not the email exists, with equivalent computational work performed on both paths (e.g. always the same hash/compare cost, or always enqueuing the same background email-send job regardless of account existence) — not a `Thread.Sleep`/artificial-delay mechanism; the outbound password-reset email itself reveals nothing account-state-specific to a third party; an automated test asserts response equivalence, not just code review; a route inventory/grep confirms no live, reachable platform-admin-facing route exists anywhere in Phase 1 code. **JWT signing-key security:** the signing secret is never committed to source control (verified by `.gitignore` + WP-9's CI grep check); the production signing key is sourced only from environment variables/host secret storage, never `appsettings.json`; minimum HMAC-SHA256 with ≥256-bit key, or RS256/ES256 if key rotation across services is anticipated; a rotation path is documented (versioned `kid`, validating tokens signed with a prior key during a rotation window); the application fails closed at startup if a required production signing secret is missing or below the minimum length — it must never fall back to a default/dev key silently.
- **QA requirement:** Test suite covering token expiry, refresh rotation/reuse-detection, lockout-after-N-failed-attempts (threshold set by Backend per §31, no owner input needed), the platform-admin/tenant mutual-exclusion assertion via test-only token construction, and the password-reset response-equivalence assertion.
- **Security-review requirement:** Required — highest-risk Phase 1 surface. Review password hashing algorithm choice, refresh-token-at-rest hashing (never stored raw), rate-limit thresholds, and the platform-admin isolation guarantee end-to-end (via test tokens). Additionally: confirm JWT signing-key handling meets the security bar above; **explicitly approve the specific anti-enumeration implementation approach chosen before it ships** (equivalent-work mechanism, not artificial delay); confirm via route inventory that no live platform-admin-facing route exists in the shipped code.

### WP-5 — Authorization Framework
- **Objective:** Implement the policy-based requirements/handlers architecture specified in the expanded §28: `IAuthorizationRequirement` + `AuthorizationHandler<T>` pattern supporting role, permission, contextual, amount-based, tenant-boundary, and resource-ownership checks. Phase 1 concrete policies: `DiscountLimitHandler` (Manager discount cap ≤15%) and `EstimateApprovalThresholdHandler` ($500 estimate-approval-required rule, applies to whichever role creates/sends the estimate, per the earlier permission-matrix fix).
- **Responsible specialist:** Backend Engineer (with Technical Architect sign-off on the extensibility shape)
- **Dependencies:** WP-3, WP-4.
- **Files/modules created:** `Authorization/Requirements/*.cs`, `Authorization/Handlers/*.cs`, policy registration in `Program.cs`, mechanic-scope and tenant-boundary handlers per §6/§29.
- **Acceptance criteria (rewritten — scope correction, backend-engineer + qa-automation-engineer):** `DiscountLimitHandler` and `EstimateApprovalThresholdHandler` are implemented as real, unit-testable authorization handlers and exercised at the **handler/application-service level**, not via new Phase 3 estimate/job HTTP endpoints — those endpoints don't exist yet in Phase 1, and this WP must not invent new product rules or premature endpoints to test against. Endpoint-level authorization tests are explicitly deferred to the phase that ships the real protected endpoint (§19 — Estimate API), to be added there when that endpoint is built. A Manager-attempted discount >15% is rejected server-side regardless of client-side UI state (tested at the handler/service level); an estimate >$500 from any role routes to "Pending Owner Approval" and cannot be sent until approved (tested at the handler/service level); a mechanic removed from a job immediately loses access to that job's child records (tasks/parts/photos), not just the job record; adding a new future contextual rule is demonstrably a single new handler class with no changes to existing handlers (extensibility spot-check, not a generic rules engine). **Authorization bypass protection (security finding — HIGH):** any value gated by these two handlers (discount %, estimate total crossing $500) must be mutable through exactly **one** application-service code path that invokes the policy check — never bypassable via a generic PATCH/update endpoint, a bulk-update endpoint, an alternate service method, or a seed/migration/data-import path. At implementation time, explicitly review and account for: any generic entity-PATCH endpoint, any generic update-estimate/update-job endpoint, any bulk-update operation, any repository/service method that could set `discount_percent`/`estimate.total`/`subtotal` outside the dedicated service methods, and any seed-data or migration script that writes those columns directly. Acceptance requires a test that attempts to set a >15% discount or a >$500 estimate through every other available write path, asserting each either rejects it outright or itself routes through the same policy check. **Standing Rule (see also the "Standing Rules" section):** this single-mutation-path requirement is not a one-time Phase 1 check — it must be re-verified by whichever future phase (§19, Estimate API) adds the first real PATCH/bulk-update endpoint capable of touching these columns, before that endpoint is considered complete.
- **QA requirement (rewritten):** Mandatory boundary-value tests, exactly: discount **15.00%** (non-Owner, otherwise qualifying) → permitted; discount **15.01%** → denied; Owner discount **>15%** → permitted, per DECISIONS.md #7; estimate **$500.00** → does not route to Pending Owner Approval; estimate **$500.01** → routes to Pending Owner Approval, applying regardless of actor role, per §28; unauthorized-role case → denied; tenant-mismatch case (actor `garage_id` ≠ resource `garage_id`) → denied. Plus the bypass-path tests described above. Plus the full permission-matrix test coverage begun here and extended as later phases add roles/actions.
- **Security-review requirement:** Required — this is the core privilege-escalation surface. Confirm the Accountant "Admin"-label fix and Mechanic PII-omission rule from the permission-matrix reconciliation are correctly enforced here, not just documented. Confirm the single-code-path bypass-protection requirement above is actually satisfied — walk every write path capable of touching `discount_percent`/estimate totals and confirm each is either the dedicated service method or itself routes through it.

## Standing Rules

**Tenant-isolation coverage for new resources.** Any future work package that introduces a new tenant-owned resource (any table carrying `garage_id`) is not complete until tenant-isolation tests for that resource exist and pass. This rule applies for the lifetime of the project, not just Phase 1. Concretely: when Expenses (Phase 4), Attachments (V1.1), or any other new `garage_id`-bearing table ships, the work package that introduces it must include tenant-isolation tests for it — following the same pattern established in WP-3 (cross-tenant query returns zero rows/404/403; `garage_id` cannot be client-supplied) — as part of its own acceptance criteria, not as a follow-up.

**Single-mutation-path enforcement for protected/authorization-gated values.** The same "exactly one authoritative code path, no bypass via generic PATCH/bulk-update/alternate service/seed path" pattern established for WP-3B (`garages` inserts) and WP-5 (discount %, estimate total) applies to every future authorization-gated business value. Whichever work package first adds a real write endpoint capable of touching a value already gated by an existing `AuthorizationHandler` (e.g. §19 Estimate API adding real PATCH/update endpoints) must re-verify the bypass-protection test for that value as part of its own acceptance criteria before it is considered complete.

**Follow-up flagged, not made here:** this Standing Rule should be mirrored into `11_engineering_handoff.md` §63 (Testing Strategy) and §69 (Definition of Done), since both currently describe tenant-isolation testing as a Phase 1 checklist item rather than a durable, project-lifetime rule. That edit is out of scope for this pass — `11_engineering_handoff.md` is a reference document this plan does not modify — and is flagged here for a future editing pass on that document.

## Phase 1 Quality Gates

**Pipeline:**

```
PHASE 1 IMPLEMENTATION
  → AUTOMATED TEST SUITE (CI-enforced, WP-9)
  → QA GATE (qa-lead)
  → REMEDIATION (owning engineering agent)
  → SECURITY GATE (security-reviewer)
  → REMEDIATION
  → DISPATCHER ACCEPTANCE REVIEW
  → OWNER
```

Each gate is a hard stop. Only the gate owner who raised a finding may clear it. No stage — including Dispatcher Acceptance Review — may waive a QA or Security finding for schedule reasons.

### QA Gate severity definitions (qa-lead)

**BLOCKER:**
- A tenant-isolation failure in any WP-3/WP-3B-scoped resource.
- An authentication/authorization bypass, including platform-admin/garage-tenant conflation.
- Backend or frontend fails to build.
- CI does not actually execute the WP-3/WP-5 suites on every PR — a suite that exists but isn't wired into CI is BLOCKER, not lesser.
- Any test required by §63/WP-5 acceptance criteria that is absent, stubbed, or skipped without a documented, Owner-approved Phase-3 deferral recorded in this document.

**CRITICAL:**
- Missing boundary-value coverage on an otherwise-correctly-enforced authorization rule.
- A "grep/manual-verifiable" check with no automated enforcement, where the underlying rule is security/isolation-relevant.
- A flaky test masking a real failure.

**Non-gating (tracked, does not block):** code style; missing non-security coverage on scaffold-only code; documentation gaps; performance concerns with no correctness impact; UI/UX findings (moot in Phase 1 — no product UI ships in this phase's scope beyond scaffolding).

### Security Gate severity definitions (security-reviewer)

Any CRITICAL or HIGH finding blocks acceptance regardless of QA status, until fixed and re-reviewed.

**CRITICAL:**
- Tenant-isolation bypass.
- Authentication bypass (forged/absent JWT accepted).
- A secret committed to source control or logged in plaintext.
- Platform-admin/garage-tenant mutual-exclusion failure.
- A SQL injection vector (unparameterized query built from user input) — see §58.
- CORS misconfiguration permitting arbitrary origins with credentials (e.g. `AllowAnyOrigin` + `AllowCredentials`, or a production origin allowlist that isn't actually enforced) — see §59.

**HIGH:**
- Authorization bypass on a specific rule (discount %/$500-threshold enforceable client-side only, or via an alternate write path, including a seed/migration path).
- A live customer-reachable auth surface shipped without required baseline controls.
- Refresh tokens stored/transmitted unhashed.
- Missing server-side validation allowing privilege elevation within one domain (not cross-tenant).

**MEDIUM/LOW (non-gating, tracked):** missing defense-in-depth; verbose error messages; non-security-critical hardcoded config; test-coverage gaps not tied to an exploitable path.

### Scope confirmation

No production deployment is part of Phase 1 (per `DECISIONS.md` #5; WP-9 explicitly excludes a deployment step). This gate pipeline evaluates code/test quality only — it is not a production release gate. A future phase's deployment needs its own separate release gate, defined when hosting is decided.
